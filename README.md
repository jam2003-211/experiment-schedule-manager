# 実験スケジュール管理

研究データを外部送信せず、ブラウザ内だけで実験アイデア、工程、逆算スケジュール、複数実験の資源制約付き最適化を管理する日本語Webアプリです。現在は「第4段階：来室日数を考慮した複数実験最適化」まで実装しています。

## 起動方法

追加インストールは不要です。`index.html` をブラウザで開いてください。

より安定した動作確認には、このフォルダでローカルHTTPサーバーを起動します。

```powershell
python -m http.server 8000
```

その後、ブラウザで `http://localhost:8000` を開きます。Pythonがない場合は `npx serve .` でも起動できますが、初回に外部パッケージを取得する場合があります。

- 実験名・目的・材料・装置・メモの検索、ステータス絞り込み、優先度などによる並べ替え
- 件数と状態別の集計
- 入力値検証、削除前確認、関連計画がある場合の影響件数表示

- 開始時・終了時・待機確認時の来室要否と確認間隔の登録
- 自己参照、存在しない先行工程、循環依存、不正時間の保存防止

- テンプレートと各個別計画の工程を独立して編集
- 個別実験計画の工程表示順を上下ボタンで変更し、依存関係とは分離して保存
- 曜日別の作業可能時間、手動休日、日付別例外の設定
- 完成予定日時からの工程スケジュール逆算

- 計算時点の作業可能時間設定をスケジュールへ保存
- 複数実験を異なる完成予定日時・優先度で一括スケジューリング
- 同一作業者、装置容量、装置利用不可期間、作業者利用不可期間の競合回避
- 作業時間と装置占有時間の独立管理。複数装置、作業終了後の占有、常時監視に対応
- 中断可能工程の作業枠分割と、中断不可工程の連続枠検証

- 通常日、可能なら休みたい日、来室不可日の設定と、自宅作業プロファイル
- 最短完成プランと来室日数削減プランの比較、実際の完了日時、月間カレンダー、ガント表示

- 工程開始日時の手動指定と、依存関係・資源競合・期限の再検証
- 計算結果を下書きとして保存し、明示的に確定するまで確定済み計画を維持

## 使い方

1. 「実験を登録」を押し、実験名などを入力して保存します。
2. カード右上の鉛筆アイコンで編集、削除アイコンで削除します。
3. 上部の検索・絞り込み・並べ替えで一覧を整理します。
4. 「工程テンプレート」でテンプレートを作り、工程を追加します。
5. 工程では作業・待機時間、先行工程、装置占有、来室条件を設定します。
6. 「計画へ適用」で実験ストックを複数選択できます。作成後は「実験計画」で個別工程を編集できます。
   - 個別計画の「↑」「↓」は表示順だけを変更します。実施順序は鉛筆ボタンから先行工程を編集します。
7. 「作業可能時間」で曜日、休日、日付別例外を設定します。
8. 「スケジュール」で実験計画と完成予定日時を選び、「逆算する」を押します。
9. 工程一覧、月間カレンダー、ガントチャート、来室警告を確認します。
10. 「作業者・装置」で担当者、装置容量、利用不可期間を設定します。
11. 「複数実験の最適化」で2件以上の計画と各期限を選び、2つの比較プランを作成します。
12. 必要なら工程開始日時を手動入力して再計算し、採用する結果だけを「この計画を確定」で確定します。
13. 左メニューの「データ管理」でバックアップまたは復元します。

## 保存とバックアップ

データはブラウザの `localStorage` のキー `experimentScheduleManager.data` に保存します。同じPCでもブラウザや閲覧プロファイルが異なると別データになります。プライベートブラウズやブラウザデータ削除では消失することがあるため、定期的に「JSONを保存」してください。

復元ではJSONを検証し、対応スキーマ（現在はv4）、主要コレクションの型、必須値、日時、ID重複、工程・計画・作業者・装置などの参照整合性を確認します。不正なv4データを空配列や初期値へ補正せず、日本語の理由を表示して拒否します。検証が完了するまで保存済みデータは変更しません。正常なv1・v2・v3データは既存値を保持してv4へ移行します。初回移行時は、移行元に応じて `experimentScheduleManager.data.preMigration.v1`、`.v2`、`.v3` のいずれかへ元のJSONを自動退避します。検証後も、上書き前に確認画面を表示します。

## データ構造

ルートに `schemaVersion` と `updatedAt` を持ち、次の領域をIDで関連付ける方針です。

- `experimentIdeas`: 実験ストック
- `templates`: 工程テンプレートの名前と説明
- `plans`: 実験ストックと元テンプレートを参照する個別計画
- `steps`: `ownerType` と `ownerId` によりテンプレートまたは個別計画へ所属する工程
- `availability`: タイムゾーン、場所別プロファイル、曜日設定、休日、日付別例外
- `equipment`: 工程からID参照される装置、同時利用容量、利用不可期間
- `workers`: 作業者、研究室・自宅の作業可能時間プロファイル、利用不可期間
- `attendancePreferences`: 日付ごとの通常／可能なら休みたい／来室不可
- `scheduleVersions`: 逆算結果、警告、工程区間、来室日、計算時点の作業可能時間スナップショット
- `optimizationRuns`: 対象計画、探索条件、入力スナップショット、診断情報
- `optimizationResults`: 最短完成／来室日数削減の下書き・確定候補と全工程・資源予約
- `confirmedOptimizationResultId`: ユーザーが明示的に確定した最適化結果

## 逆算計算

依存関係を検証してから逆トポロジカル順にたどり、後続工程の開始日時を先行工程の期限として計算します。作業は作業可能枠だけを消費し、枠を超えた分は前の作業可能日へ繰り越します。工程内では作業終了と待機開始を同じ日時に固定します。

暦時間待機は休日・夜間も連続して経過します。作業可能時間待機は設定された枠だけで進みます。暦時間待機の終了や確認が作業不可時間に重なり、来室が必要な場合は元の日時を維持して警告します。ユーザーの許可なく日時を移動しません。

日時はUTCのISO文字列として保存し、各スケジュールに保存したタイムゾーン（現在は `Asia/Tokyo`）で入力・表示します。作業可能時間は `profiles` 配列で保持し、研究室と自宅を別プロファイルとして設定できます。

各計算結果は作業可能時間、休日、日付別例外の完全なコピーを保持するため、その後に設定を変更しても過去の表示は変わりません。

### 工程データ

工程では、将来のスケジュール計算用に次の値を分離しています。

- `workDurationMinutes`: 作業者が拘束される作業時間
- `waitDurationMinutes`: 別実験を進められる待機時間
- `waitDurationType`: 休日中も進む `calendar` または作業可能時間だけ進む `working`
- `predecessorIds`: 先行工程ID
- `equipmentRequirements`: 装置ID、表示名、作業開始からの占有開始・終了オフセット、常時監視の要否
- `labRequirement`: 開始時、終了時、待機確認時それぞれの来室要否
- `waitCheckIntervalMinutes`: 待機確認の間隔
- `waitCheckDurationMinutes`、`waitCheckWorkerId`、`waitCheckRequiresLab`: 定期確認の所要時間、担当者、場所
- `assignedWorkerId`、`workLocation`: 作業担当者と研究室／自宅
- `interruptible`: 作業可能枠をまたいで中断・再開できるか
- `status`、`actualStartedAt`、`actualEndedAt`、`remainingWorkMinutes`: 進捗・実績・残り時間
- `manualStartAt`: 手動指定した工程開始日時

待機時間は画面上では日・時間・分に分けて入力し、保存時に `日 × 1440 + 時間 × 60 + 分` で合計分へ変換します。既存の分単位データとJSONバックアップ形式は変更しません。

計画作成時はテンプレート工程を新しいIDで複製し、先行工程IDも複製先へ張り替えます。以後の編集は相互に影響しません。

## 第4段階の最適化

必須条件として依存関係、場所別作業可能時間、来室不可日、作業者・装置容量、実験ごとの完成予定日時を検証します。優先度は候補順序に使いますが、低優先度でも期限超過を許容しません。

最短完成プランは、全実験の最終完了日時（メイクスパン）を最小化し、同値なら各実験の完了日時合計を小さくします。来室日数削減プランは、必須制約を再検証した候補と最短完成プランをまとめて比較し、来室日数、「可能なら休みたい日」への来室日数、最終完了日時の順で小さくします。このため、同じ評価順で最短完成プランより不利な候補は採用しません。いずれも期限順・優先度順の複数ヒューリスティック候補から選ぶ近似解であり、最適性は保証しません。

探索には5〜20秒の上限を設定できます。連続作業枠不足、循環依存、存在しない計画・工程、無効な手動開始など論理的に証明できる場合は「実行不可能」と表示します。組合せ探索が時間上限に達した場合は「探索制限内で解を発見できません」と区別します。

## 既知の制限

- 最適化は決定的なヒューリスティック探索で、全組合せを列挙する厳密最適化ではありません。
- 粒度は15分または30分です。入力時間が粒度に一致しない場合、作業開始候補は次の粒度境界へ切り上げます。
- 自動計算のキャンセルはHTTPサーバー経由ではWeb Workerを停止します。`file://` で直接開いた場合は同期フォールバックのため、計算中の即時中断はできません。
- 進捗変更後は影響する後続工程を表示し、次回の一括最適化で再計算します。自動で確定済み計画を置き換えることはありません。
- カレンダー画面は長期計画の先頭6か月を表示しますが、保存データには全期間を保持します。

```powershell

```

## GitHub Pagesで公開する

このアプリはビルドを必要としない静的サイトです。GitHubへリポジトリを作成して内容をpushした後、リポジトリの **Settings → Pages** を開き、**Build and deployment** で **Deploy from a branch** を選択します。公開対象のブランチと `/(root)` を選んで保存すると、リポジトリ直下の `index.html` が公開されます。

プロジェクトサイトとして公開した場合、URLは通常次の形式です。

```text
https://<GitHubユーザー名>.github.io/<リポジトリ名>/
```

アプリ内のCSS、JavaScript、Web Workerは相対パスで参照しているため、`<リポジトリ名>` のサブディレクトリ配下でも読み込めます。

### localhostから公開URLへデータを移行する

`localStorage` はURLのオリジンごとに別の保存領域です。`http://localhost:8000` に保存したデータは、GitHub Pagesの `https://<GitHubユーザー名>.github.io` から自動では読み込めません。また、ブラウザや閲覧プロファイルが異なる場合も別の保存領域になります。

移行前に、localhostで使用しているアプリの「データ管理」を開き、必ず「JSONを保存」でバックアップを作成してください。その後、GitHub Pagesの公開URLを開き、「JSONから復元」で保存したファイルを選択し、内容を確認して復元します。公開URL側でデータを確認できるまでは、元のlocalhostのデータとJSONバックアップを削除しないでください。

JSONバックアップには実験データや設定が含まれます。リポジトリへ追加したりGitHubへpushしたりせず、安全なローカル保存先で管理してください。

## 制約

- 保存容量はブラウザの `localStorage` 上限（一般に数MB程度）に依存します。工程・実績が増えて不足する場合は、ローカルのIndexedDBへの移行が候補です。
- サーバー、クラウド同期、外部API、OS通知は使用していません。
- 祝日データは将来段階でも自動取得せず、手動登録する設計です。
